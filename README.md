# server-audit

Универсальный bash-скрипт диагностики Linux-сервера. Сам определяет, что
установлено (nginx/apache, MySQL/PostgreSQL/Redis/MongoDB, Docker,
WireGuard, панели управления и т.д.), проверяет ресурсы, сеть, домены,
логи ошибок и статус найденных сервисов — и в конце печатает в терминал
один структурированный отчёт, который остаётся только скопировать и отдать
на анализ (человеку или нейросети).

Пока идёт сбор, в терминал выводятся короткие пометки прогресса
(`[*] проверяю ...`), чтобы было видно, что скрипт работает. Сам отчёт со
всеми данными выводится один раз, цельным блоком, в самом конце. **На диске
сервера ничего не остаётся** — все промежуточные файлы временные и
гарантированно удаляются (`shred`) при выходе, даже по Ctrl+C.

Работает на systemd-дистрибутивах (Ubuntu, Debian, CentOS/RHEL/Alma/Rocky и
т.д.) в полном объёме, на не-systemd системах (OpenRC/SysV) — с автоматическим
переключением на альтернативные способы проверки статуса сервисов и логов,
без падений скрипта целиком.

Объём отчёта ограничен (логи проблемных Docker-контейнеров — не больше 8 шт.
по 15 строк, общий отчёт — не больше 3000 строк с явной пометкой, если что-то
обрезано), чтобы даже при каскадном краш-лупе сервисов отчёт не раздувался до
неподъёмных размеров и не обрывался в буфере прокрутки терминала.

## Запуск

Одной командой:

```bash
curl -fsSL https://raw.githubusercontent.com/lyfreedomitsme/server-audit/main/server_audit.sh | sudo bash
```

Не всё требует root, но часть проверок (auth.log, `sshd -T`, iptables,
crontab root) без него будут пропущены — скрипт сам об этом предупредит и
продолжит работу.

Если хотите сначала посмотреть, что именно будет выполняться на сервере —
скачайте файл отдельным шагом перед запуском:

```bash
curl -fsSL https://raw.githubusercontent.com/lyfreedomitsme/server-audit/main/server_audit.sh -o server_audit.sh
sudo bash server_audit.sh
```

## Что проверяется

- ОС, дистрибутив, init-система, uptime, load average
- CPU / память / swap, `iostat`/`mpstat` (если установлен `sysstat`), топ
  процессов по RAM и CPU
- Диск, inode, LVM
- OOM killer и ошибки ядра (dmesg)
- Упавшие сервисы (systemd / OpenRC / SysV — в зависимости от того, что есть
  на сервере), лог ошибок за 24ч (journalctl или syslog/messages)
- Сеть: интерфейсы, маршруты, DNS, ping/traceroute/HTTPS-исходящий трафик,
  открытые порты, firewall (ufw/iptables/nftables/firewalld)
- SSH: статус, конфиг, активные сессии, попытки логина, fail2ban
- Панели управления (HestiaCP, ISPmanager, FastPanel, DirectAdmin, aaPanel, VestaCP)
- nginx / apache
- **Домены**: список доменов из конфигов nginx/apache + сверка их A-записей
  с внешним IP сервера (указывает ли DNS домена реально на этот сервер)
- PHP-FPM
- MySQL/MariaDB, PostgreSQL, Redis, MongoDB
- Docker: контейнеры, логи падающих/unhealthy контейнеров
- SSL-сертификаты (certbot)
- WireGuard, известные прокси-контейнеры (3x-ui, hysteria, mtproxy, teamspeak)
- cron root

## Публикация на termbin.com (опционально)

После вывода отчёта скрипт в интерактивном режиме спрашивает:

```
Опубликовать отчёт на termbin.com? Ссылка публичная, без пароля,
будет активна 15 сек. — скрипт сам её удалит.
y/N:
```

По умолчанию (просто Enter, или что угодно кроме `y`) — ничего никуда не
уходит. Если ответить `y` — отчёт заливается на termbin.com, ссылка
выводится в терминал, и через 15 секунд скрипт сам её удаляет (реальное
удаление через API термбина `POST /delete?slug=...`, не имитация). Удалить
раньше можно вручную — готовая команда выводится сразу под ссылкой.

**Это не приватно**: ссылка публичная, без пароля — кто угодно, у кого она
окажется (или кто её угадает/переберёт — см. ниже), сможет её открыть.
Пароли/токены уже вырезаны фильтром, но хостнеймы/IP/список софта останутся
видны.

О "случайно угадать/перебрать ссылку за 15 секунд": id термбина — это всего
4 символа (`a-z0-9`, ~1.7 млн комбинаций), причём генератор кода termbin
(проект [fiche](https://github.com/solusipse/fiche)) — не криптографически
случайный: он использует `rand_r()`, засеянный один раз временем запуска
процесса сервера. Это слабее, чем хотелось бы, но мы это не контролируем —
id генерирует сервер termbin, клиент на это не влияет. Случайный прохожий
или бот-сканер физически не подберёт ссылку за 15 секунд, но это не
криптостойкая защита — только обфускация коротким сроком жизни. Не
публикуйте так данные, которые не готовы потерять при неудачном стечении
обстоятельств.

Переменные окружения для неинтерактивного запуска (без вопроса):
- `PASTE=1` — публиковать без вопроса.
- `PASTE=0` — не публиковать без вопроса.
- `PASTE_TTL=<секунды>` — своё время жизни ссылки вместо 15 сек по умолчанию.

## Переменные окружения

- `SKIP_NET=1` — пропустить внешние сетевые проверки (ping/traceroute/curl),
  полезно на серверах с ограниченным исходящим трафиком.

## Если терминал обрезает отчёт

Отчёт может быть длинным, а у многих SSH-клиентов маленький буфер прокрутки
по умолчанию (у PuTTY — вообще 200 строк). Это ограничение клиента, а не
скрипта — сам отчёт в скрипте уже ограничен разумным объёмом (см. ниже).
Самый надёжный способ получить его целиком:

```bash
ssh root@SERVER_IP 'curl -fsSL https://raw.githubusercontent.com/lyfreedomitsme/server-audit/main/server_audit.sh | bash' > report.txt
```

Запустите это с локального терминала (не изнутри уже открытой сессии на
сервере) — `report.txt` появится у вас на компьютере целиком, без обрезаний,
и ничего не остаётся на сервере. Сам скрипт в конце своего вывода подставляет
эту команду с уже готовым IP сервера — просто скопируйте её оттуда.

Альтернативы: увеличить буфер прокрутки в настройках терминала (в PuTTY —
Window → Lines of scrollback), включить логирование сессии в файл (есть в
PuTTY/MobaXterm в настройках сессии), либо `PASTE=1` (см. выше).

## Безопасность

- На диске сервера ничего не сохраняется. Данные собираются во временный
  буфер в `/tmp` (права `600`), очищаются от секретов, печатаются один раз
  в терминал — и временные файлы гарантированно затираются (`shred`) через
  `trap ... EXIT`, даже если скрипт прервать по Ctrl+C.
- Перед выводом отчёт прогоняется через фильтр, который вырезает похожие
  на пароли/токены/API-ключи/приватные ключи значения (`password=`,
  `-pPASSWORD` у mysql/psql/mongodump, `Authorization`/URL с basic-auth,
  AWS access key, PEM-блоки приватных ключей). WireGuard-ключи скрывает сама
  утилита `wg`.
- Это фильтр "на всякий случай", а не гарантия конфиденциальности — прежде
  чем отправлять отчёт куда-то за пределы своей команды, просмотрите его.
- Пароли намеренно не показываются в открытом виде: для диагностики важен
  сам факт ошибки (`connection refused`, `authentication failed` и т.п.), а
  не значение пароля — а вот случайно засветить реальный пароль в чате с
  ИИ или в тикете поддержки — риск без всякой пользы для диагностики.
- В скрипте не используется `eval` — все команды выполняются через
  `bash -c` со статическими, зашитыми в сам скрипт строками (внешний ввод
  никогда в них не попадает).

Скрипт ничего никуда не отправляет сам — только читает состояние сервера и
выводит текст в терминал, которым запущен.
